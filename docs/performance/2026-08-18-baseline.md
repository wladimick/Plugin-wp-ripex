# RIPEX Performance Baseline — 2026-08-18

## Purpose

Freeze the pre-optimization state of RIPEX so the same measurements can be repeated after each performance release and used in a before/after client report. This baseline was captured on **18 August 2026** before any performance code from this branch was deployed to production.

## Production context

- Public URL: `https://ripex.cl`
- WordPress physical root: `/home/ripex/public_html/portal`
- Platform: WordPress + WooCommerce
- RIPEX Portal: `1.5.14`
- Hosting: shared cPanel/WHM node on Azure VM
- OS: CloudLinux 9.8
- cPanel account: `ripex`
- Production PHP: 8.3
- PHP-FPM: `ondemand`, `pm.max_children=2`, `pm.max_requests=20`, `pm.process_idle_timeout=10`
- Staging: PHP 8.3, max 1 child
- Test: PHP 8.0, max 1 child

### CloudLinux/LVE limits

| Resource | Limit |
|---|---:|
| CPU / SPEED | 100% (~one logical CPU worth of quota) |
| Physical memory | 1024 MiB |
| Entry processes | 20 |
| NPROC | 100 |
| I/O | 1024 KB/s |
| IOPS | 1024 |

Historical evidence available before this baseline records **99 RIPEX LVE/cgroup OOM events**. These are account-level memory exhaustion events, not 99 global server outages.

## Azure host observed

- 8 logical CPUs
- 4 physical cores / 2 threads per core
- Intel Xeon Platinum 8272CL @ 2.60 GHz
- ~15.7 GiB RAM
- 8 GiB swap; ~4.16 GiB allocated during the test window

The VM is shared with other cPanel accounts, therefore host CPU/load cannot be attributed exclusively to RIPEX.

## Functional snapshot before optimization

Manual navigation confirmed these functions worked before changes: Pedidos/pagination, order detail, Inventario, Reportes, Clientes, Carritos, Crear pedido and product/customer search. The Pedidos UI showed approximately **1,272 orders / 43 pages**. Client-facing behavior and report results must remain equivalent after optimization.

## Test A — normal portal navigation

**Window:** 13:28:22–13:30:06 UTC.  
**Sequence:** Pedidos → next page → order detail → Inventario → Reportes → Carritos.

Observations:

- two production PHP-FPM workers concurrently;
- early concurrent CPU approximately 44.6% + 42.0%;
- typical worker RSS ~170–191 MiB;
- one worker spiked to **435,796 KiB RSS (~426 MiB)**;
- host still had several GiB available RAM.

Because multiple sections were visited, this test could not attribute the memory spike to a single endpoint.

## Test B — isolated Reportes

**Window:** 13:40:34–13:41:50 UTC.  
**Action:** only open Portal Pedidos → Reportes and wait for completion.

| Stage | Main worker | Second worker | Approx. combined PHP RSS |
|---|---:|---:|---:|
| Initial | ~185–197 MiB | ~181 MiB | ~366–378 MiB |
| Before peak | ~211 MiB | ~154 MiB | ~365 MiB |
| **Report peak** | **442,408 KiB (~432 MiB)** | **157,920 KiB (~154 MiB)** | **~586 MiB** |
| After peak | ~275 MiB | ~161 MiB | ~436 MiB |

A single Reportes request therefore reached roughly **42% of the entire 1 GiB LVE memory allowance** by itself. Two similarly heavy PHP requests could approach ~864 MiB before any other account process is included.

### Host CPU during Reportes

`vmstat` showed point samples with run queue above the 8 logical CPUs and host CPU nearly fully busy, including approximately `us=85 sy=15 id=0 wa=0` and `us=84 sy=14 id=2 wa=0`. This proves shared-host CPU contention existed during the window, but does **not** prove RIPEX alone caused it.

### I/O and swap

- `iowait` was generally 0%, with only small isolated values;
- no sustained swap-out was observed;
- a small isolated swap-in occurred;
- the 1 MiB/s LVE I/O limit remains a risk to monitor, but Test B did not demonstrate disk wait as the primary Reportes bottleneck.

## Confirmed application root cause — Reportes

In 1.5.14 the original `ajax_get_reports()`:

1. runs an unbounded `WC_Order_Query` with `limit => -1`;
2. materializes the complete order history as WooCommerce order objects;
3. builds customer history and only then applies the selected report period in PHP;
4. runs an unbounded `WC_Product_Query` with `limit => -1`;
5. materializes the complete published product set for stock/no-movement calculations.

The isolated test reproduced the same ~430 MiB worker peak seen during general navigation. **Reportes is P0-confirmed for optimization.**

Every later test should also record browser DevTools duration/TTFB for `ripex_portal_get_reports`; this client-side timing was not captured in the first baseline.

## Client-facing interpretation

> A normal authenticated Reportes request could consume approximately 432 MiB in one PHP worker while RIPEX was constrained to 1 GiB for the whole account and only two production PHP workers. This creates a credible path to queueing, throttling and memory exhaustion under modest concurrency. The optimization program therefore reduces application work per request first and then re-evaluates infrastructure using the same repeatable tests.

## Measurement limitations

- `lveinfo`/LVE-Stats is not installed on this node, so historical per-resource fault counters were unavailable through that command.
- `/proc/lve/list` exposed a header but the initial UID filter did not return the RIPEX row; no LVE-fault claim is made from that capture.
- Browser Network timing was not captured in the first baseline.
- Host CPU metrics include all accounts on the shared cPanel VM.
